# 循优——C2B2C 二手商品循环交易平台开发文档

## 1. 项目概述

循优是一个面向个人用户、平台运营人员和二手买家的 C2B2C 二手商品循环交易平台。平台将“用户回收—平台质检/估价—二次标准化销售—买家购买—物流履约—评价反馈”串成闭环，减少闲置商品流转中的人工校验和信息不对称。

本人主要负责商品信息、用户管理、回收流程、物流追踪、积分、AI 图片审核、SN 信息解析、自动估价及二销订单等基础支撑模块。

## 2. 技术架构

项目采用 Spring Boot 3.5 单体架构，Controller 负责协议适配，Service 负责业务编排和事务边界，Repository 负责数据访问，Provider 负责百度 AI、物流等外部依赖适配。持久层使用 Spring Data JPA，开发环境支持 H2，生产环境使用 MySQL；认证使用 Spring Security + JWT，前台详情页使用 FreeMarker 静态化渲染。

```text
浏览器/后台管理端
        ↓ HTTP/JSON
Controller → Application Service → Domain Service → Repository → MySQL/H2
                                  ↓
                         Provider(百度AI/物流)
```

## 3. 核心数据模型

主要表及关系如下：

| 表 | 作用 | 关键关联 |
|---|---|---|
| `user_account` | 用户、角色、等级、积分 | 一对多回收单、二销订单、积分流水 |
| `product` | 商品基础信息、SN、品牌、型号、成色 | 一对多图片；被回收单引用 |
| `recycle_order` | C 端回收单及回收状态 | `user_id`、`product_id` |
| `logistics_track` | 回收/发货物流轨迹 | `order_id`、物流单号 |
| `points_ledger` | 积分变动流水 | `user_id`，用原因字段关联业务单号 |
| `valuation_rule` | 品牌/型号/生产年限/成色估价规则 | 被估价服务按优先级匹配 |
| `resale_listing` | 标准化后的二销商品 | 关联回收单/商品 |
| `resale_order` | 买家购买订单 | `buyer_id`、`listing_id` |
| `resale_review` | 订单评价、追评和商家回复 | 关联订单及商品 |
| `auth_refresh_token` | Refresh Token 会话 | 用户、设备维度管理 |
| `auth_token_blacklist` | Access Token 撤销 | 通过 `jti` 判断失效 |
| `operation_audit_log` | 管理操作审计 | 记录动作、目标、操作者和上下文 |

设计原则：商品信息与交易单据分离，回收价格保存快照，避免规则调整后历史订单金额变化；积分采用流水表记录增量，账户表保存当前余额，便于对账；高频状态字段使用枚举字符串并由服务层统一校验状态流转。

## 4. 登录、Token 与权限认证

### 4.1 登录流程

1. 客户端提交用户名、密码和设备号到 `POST /api/auth/login`。
2. `AuthenticationManager` 调用 `UserDetailsService` 查询 `user_account`，校验账号状态为 `ACTIVE`，使用 `PasswordEncoder` 校验密码。
3. 登录成功后生成 Access Token 和 Refresh Token。JWT 中包含 `sub`、`jti`、`role`、签发时间和过期时间。
4. Refresh Token 以哈希或不可逆标识落库，同时绑定用户名和设备号，形成可撤销的多设备会话。
5. 记录登录审计和安全事件，返回两个 Token 及过期时间。

### 4.2 刷新与登出

Refresh 时校验 Token 是否存在、未过期、未撤销且设备号匹配；成功后撤销旧 Refresh Token 并签发新 Token，防止 Refresh Token 重放。登出时将 Access Token 的 `jti` 写入黑名单，并可撤销当前设备或全部设备会话。

### 4.3 权限控制

`SecurityConfig` 使用无状态 Session，公开登录、刷新和支付回调接口；`/api/admin/**` 要求 `ROLE_ADMIN`；回收、商城、个人会话接口要求已认证。JWT 解码后把 `role` 转换为 Spring Security 的 `ROLE_xxx`，未登录返回 401，无权限返回 403。生产环境应将 JWT 密钥放入配置中心或密钥服务，演示账号密码必须改为 BCrypt。

## 5. 回收核心流程

```text
上传图片 → 百度AI审核 → SN解析 → 查询估价规则 → 生成回收单
       → 生成物流单号 → 创建物流轨迹 → 写入积分流水 → 更新用户积分
       → 后台质检 → 价格复核 → 发布二销商品
```

`RecycleApplicationService` 作为应用层门面，编排回收、上架、订单、评价等能力。创建回收单时先调用 `AiAuditService`，通过 `ImageAuditProvider` 屏蔽真实百度接口与 Mock 实现；再由 `SnParseService` 生成商品草稿，交给 `ValuationService` 计算品阶和价格，最后在事务中保存商品、回收单、物流和积分数据，并写审计日志。

状态采用有限状态机：`CREATED → QUALITY_CHECKED → PRICE_REVIEWED → LISTED`。每个动作先校验当前状态，禁止跳过质检或重复操作。

## 6. 估价机制

估价输入包括生产日期、品牌、型号和成色分数。服务先计算商品使用月数，再查询品牌/型号规则，规则支持具体品牌/型号和 `ALL` 通配；在满足年限与成色区间的规则中选择优先级最高者，输出 `GOOD`、`MEDIUM` 或 `UNQUALIFIED` 及初始价格。没有匹配规则时按使用月数执行兜底策略。

面试时应强调：估价规则放在数据库而不是写死在 Controller 中，便于运营调整；回收单保存估价快照，后续人工复核可以覆盖等级和价格；规则变更应记录版本、操作者和生效时间，避免历史数据不可追溯。

## 7. 积分、物流与外部服务

积分公式为：基础分 + 用户等级加成 + 回收频次加成，频次加成设置上限，避免异常刷分。每次变更同时写 `points_ledger`，通过业务原因和订单号对账。优化方向是增加业务幂等键和唯一索引，确保回收请求重试不会重复加分。

物流通过 `LogisticsProvider` 接口隔离第三方实现，`RealLogisticsProvider` 负责真实接口，`MockLogisticsProvider` 用于开发测试；物流状态查询更新本地快照，外部接口失败时返回上一次状态并记录告警。

百度 AI 图片审核采用 Provider 适配器。生产调用真实服务，测试替换 Mock；审核不通过直接终止回收流程，并返回明确错误码。外部调用应设置超时、重试上限、降级策略和 traceId，避免第三方阻塞数据库事务。

## 8. 二销交易与支付安全

创建订单时校验商品在售状态和库存，在事务中锁定或原子扣减库存；支付接口校验订单金额、签名、时间窗口和 nonce。支付回调先落库，再按回调流水号和幂等表防重，状态更新必须满足合法状态转换。失败回调进入重放队列，支持重试、死信和人工处置。

订单状态分为支付状态和履约状态：支付状态包括 `UNPAID`、`PAID`、`REFUNDED`，履约状态包括待支付、待发货、已发货、已完成、已取消、已退款。拆开保存可以避免“支付成功但未发货”等状态组合被错误覆盖。

## 9. FreeMarker 静态化

商品详情页将商品、成色、回收信息、评价摘要等数据组装成模板模型，由 FreeMarker 渲染 HTML。详情页适合使用缓存或按商品版本生成静态文件；商品修改、上下架和评价更新时通过版本号或缓存淘汰触发重新渲染。这样能减少 C 端重复查询和模板计算，提升首屏加载速度。需要注意模板变量默认值、XSS 转义、静态文件失效和异常回退页面。

## 10. 代码与性能优化

当前代码已经使用了应用服务分层、Provider 接口、只读事务、缓存、分页工具、乐观锁重试、统一异常码和审计日志。进一步优化建议：

1. Controller 入参改为 DTO，并使用 Bean Validation，避免大量 `Map<String,Object>` 导致类型不安全。
2. 回收创建中的 AI、SN、物流调用移出长事务，采用“业务记录 + 异步任务 + 重试”模式。
3. 积分、库存和支付幂等依赖数据库唯一索引，不能只依赖 Java 判断。
4. 列表接口统一分页，避免 `findAll()` 全表加载；为 `status、user_id、created_at、listing_id` 建组合索引。
5. JPA 查询使用投影或 fetch join，避免 N+1；缓存只缓存稳定查询结果，写操作必须精准失效。
6. 状态变化使用领域方法或状态机类集中管理，避免多个 Service 各自拼接状态。
7. 统一 traceId、结构化日志和指标，重点监控 AI 失败率、估价耗时、支付回调重放堆积和订单状态冲突。
8. 生产配置关闭默认演示凭据，JWT 密钥、百度密钥和物流密钥全部外置。

## 11. 测试重点

单元测试覆盖估价规则优先级、兜底价格、积分边界和订单状态机；集成测试覆盖登录刷新重放、管理员越权、支付回调重复通知、库存并发扣减和回收事务回滚；接口测试覆盖 401/403、参数校验、幂等重试和第三方降级。

## 12. 真实性说明

仓库当前 `SnParseService` 中仍有 Demo 解析逻辑，真实面试时应表述为“已抽象 SN 解析接口，当前 Mock/规则库实现可替换，生产接入厂商接口后返回真实品牌、型号和生产日期”，不要把尚未接入的能力描述成已经稳定上线。
